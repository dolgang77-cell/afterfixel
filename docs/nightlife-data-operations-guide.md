# VYBE 전국 클럽·파티 데이터 운영 가이드

> 이 문서는 전국 클럽/파티 데이터를 유지보수하는 운영자, 관리자, 초보 PHP 개발자를 위한 실무 기준서입니다.  
> 목표는 2가지입니다.  
> 1) 없어졌거나 오래된 장소를 빠르게 정리한다.  
> 2) 데이터를 고치다가 홈/파티/검색 화면에서 500 에러가 나지 않게 안전하게 작업한다.

---

## 1. 이 문서가 필요한 이유

VYBE의 클럽/파티 데이터는 단순히 관리자 화면에서 수동 입력만 하는 구조가 아닙니다.

- 클럽 기본 정보는 코드에 있는 큐레이션 소스에서 관리됩니다.
- 파티는 일부는 실제 확인된 이벤트이고, 일부는 "대표 운영 세션" 성격의 카드입니다.
- 홈, 파티 리스트, 검색, 비교, Near Me, 오늘밤 추천, 알림까지 같은 데이터를 여러 화면에서 재사용합니다.

즉, 한 군데를 잘못 고치면 다음 문제가 동시에 생길 수 있습니다.

- 없어진 클럽이 계속 노출됨
- 실제 특집 이벤트와 운영형 카드가 중복으로 뜸
- 파티 라벨이 혼동됨
- 홈은 500, 파티 페이지는 정상 같은 애매한 장애가 생김

그래서 운영 기준을 코드 기준으로 통일해 둬야 합니다.

---

## 2. 가장 먼저 알아야 할 핵심 구조

### 데이터 기준 파일

- 클럽/파티 큐레이션 원본: `app/Support/CuratedNightlifeData.php`
- 동기화 커맨드: `php artisan nightlife:sync-curated-data`
- 파티 분류 접근자: `app/Models/Party.php`

### 왜 관리자 화면만 보면 안 되나요?

관리자 화면(`/admin/clubs`, `/admin/parties`)은 결과를 수정하는 곳이고, 전국 큐레이션의 "원본 설계도"는 코드 파일에 있습니다.

즉:

- 관리자에서만 고치면 다음 동기화 때 다시 덮일 수 있습니다.
- 전국 단위 정리 작업은 반드시 `CuratedNightlifeData` 기준으로 고쳐야 합니다.

### 클럽과 파티는 관리 방식이 다릅니다

| 구분 | 관리 방식 | 운영 포인트 |
|------|-----------|-------------|
| 클럽 | 큐레이션 목록 직접 유지 | 폐업, 이전, 재오픈, 주소/좌표/영업시간 수정 |
| 파티 | 특집 이벤트 + 운영형 템플릿 조합 | 실제 이벤트인지, 대표 운영 카드인지 구분해야 함 |

## 3. 파티 카드 3종 분류를 반드시 이해하세요

현재 서비스는 파티를 아래 3종으로 구분합니다.

### A. `실이벤트` (`verified_event`)

뜻:
- 외부 공지, 공식 일정, Resident Advisor, 공식 채널 등으로 실제 이벤트가 확인된 카드

특징:
- `Party::$is_verified_event === true`
- `Party::$event_card_type === 'verified_event'`
- UI 배지: `실이벤트`
- 알림/검색/비교/오늘밤 추천/지도에 이 라벨이 같이 노출됨

예시:
- 특정 날짜에 DJ 라인업이 명시된 RA 특집 이벤트

### B. `운영형 카드` (`operating_card`)

뜻:
- 특정 게스트 공지가 확정된 이벤트가 아니라,
- 공식 운영시간, 예약 가이드, 최근 운영 패턴을 근거로 만든 대표 세션 카드

특징:
- `Party::$is_operating_card === true`
- `Party::$event_card_type === 'operating_card'`
- UI 배지: `운영형 카드`
- 문구도 "대표 세션", "운영 시간 기준", "공식 운영 패턴 기반"처럼 보수적으로 작성해야 함

예시:
- "매주 토요일 메인 세션"
- "주말 선셋 세션"
- "금요일 클럽 입장 세션"

### C. `일반 이벤트` (`general_event`)

뜻:
- 위 두 분류에 속하지 않는 일반 등록형 파티

특징:
- 관리자 수동 등록 파티나 별도 생성 데이터가 여기에 들어갈 수 있음
- UI 배지: `일반 이벤트`

### 절대 섞으면 안 되는 기준

- 실제 외부 이벤트 공지가 없는데 `실이벤트`처럼 쓰면 안 됩니다.
- 운영형 카드를 실제 확정 라인업처럼 쓰면 안 됩니다.
- 오래된 RA 이벤트가 끝났는데 그대로 남겨두면 안 됩니다.

## 4. 코드에서 이 분류가 어디서 정해지나요

### 파티 템플릿 분류 함수

`app/Support/CuratedNightlifeData.php`

- `rollingPartyPrefixes()`  
  운영형 카드 slug prefix 목록
- `specialPartyPrefixes()`  
  실이벤트 slug prefix 목록
- `legacyPartyPrefixes()`  
  예전 자동 생성/시드 데이터 중 삭제 대상으로 간주할 prefix 목록
- `generatedPartyPrefixes()`  
  시스템이 생성하는 prefix 전체 목록

### 모델 접근자

`app/Models/Party.php`

- `getIsVerifiedEventAttribute()`
- `getIsOperatingCardAttribute()`
- `getEventCardTypeAttribute()`
- `getEventCardLabelAttribute()`
- `getEventCardVariantAttribute()`
- `getEventCardNoticeAttribute()`

즉, 운영자가 분류를 바꾸고 싶으면 화면부터 고치는 것이 아니라:

1. `CuratedNightlifeData.php`의 prefix / 템플릿 규칙을 먼저 고치고
2. 동기화 후
3. 실제 UI 라벨이 바뀌는지 확인해야 합니다.

## 5. 파티 데이터가 만들어지는 방식

파티는 크게 2개의 소스로 만들어집니다.

### 1) 운영형 템플릿

`rollingPartyTemplates()`

이 함수는 "매주 금요일", "매주 토요일" 같은 반복 세션 카드를 만듭니다.

이때 중요한 점:

- 실이벤트가 없는 날짜를 메워 사용자 화면이 비지 않게 하는 역할입니다.
- 하지만 이것을 확정 이벤트처럼 보이게 쓰면 안 됩니다.
- 설명/라인업 문구를 매우 보수적으로 작성해야 합니다.

### 2) 특집 실이벤트

`specialParties()`

이 함수는 특정 날짜에만 존재하는 확인된 이벤트를 넣습니다.

예:
- 2026-04-24 특정 RA 이벤트
- 2026-04-25 특정 게스트 초청 이벤트

### 중복 방지 규칙

`partyRecords()`에는 이미 다음 안전장치가 들어가 있습니다.

- 같은 `club_slug`
- 같은 `event_date`
- 같은 날짜에 특집 실이벤트가 있으면
- 그 날짜의 운영형 카드 생성은 건너뜀

그래서 같은 날에:

- `운영형 카드 1개`
- `실이벤트 1개`

가 중복으로 같이 뜨지 않도록 설계되어 있습니다.

## 6. 없어진 곳을 삭제할 때 기준

전국 확장 이후 가장 중요한 운영 원칙입니다.

### 바로 비활성/삭제 후보로 보는 경우

- 공식 채널이 장기간 멈춤
- 최근 운영 흔적이 전혀 없음
- 폐점/임시휴업/이전 공지가 확인됨
- 과거 블로그 글만 남고 현재성 있는 소스가 없음

### 유지하되 주석/설명을 보수적으로 써야 하는 경우

- 과거 폐점 정보와 현재 운영 정보가 혼재함
- 재오픈/이전 후 새 주소로 운영 중
- 운영은 보이지만 일정 공지가 들쭉날쭉함

이 경우:

- `is_active`는 유지 가능
- 대신 `description`, `guide_text`, `rating_summary`에 "재검증 우선", "오래된 정보 혼재" 같은 성격을 명확히 적습니다.

### 운영형 카드에서 먼저 제거해야 하는 경우

클럽은 살아 있어도, 아래는 지워야 합니다.

- 실제 근거 없이 추정으로 만든 주간 반복 파티
- 이미 더 정확한 특집 실이벤트가 잡힌 날짜와 충돌하는 템플릿
- 과거 시드 데이터에서 남은 자동 파티

---

## 7. 오래된 자동 파티가 남아 있을 때 정리 방법

전국 데이터 정리 중 가장 많이 생기는 문제입니다.

예전 시드나 자동 생성 파티가 DB에 남아 있으면 다음 현상이 생깁니다.

- 이미 지난 파티가 계속 검색됨
- 홈/추천에서 의미 없는 데이터가 잡힘
- 같은 클럽이 같은 주말에 여러 카드로 중복 노출됨

이럴 때는 `legacyPartyPrefixes()`를 봐야 합니다.

이 목록에 포함된 prefix는 동기화 시 정리 대상으로 처리됩니다.

실무 원칙:

1. 예전에 자동 생성했던 slug prefix를 파악합니다.
2. 앞으로 유지하지 않을 prefix면 `legacyPartyPrefixes()`에 추가합니다.
3. `php artisan nightlife:sync-curated-data`를 실행합니다.
4. 지난 날짜 파티와 중복 카드가 실제로 사라졌는지 확인합니다.

## 8. 안전한 수정 순서

아무것도 모르는 PHP 개발자도 이 순서대로 하면 사고 확률이 낮습니다.

### 1단계. 수정 대상 유형을 먼저 판단

- 클럽 자체 정보 수정인가?
- 실이벤트 추가/수정인가?
- 운영형 카드 문구 조정인가?
- 오래된 자동 파티 정리인가?

### 2단계. 원본 파일 수정

보통은 `app/Support/CuratedNightlifeData.php`를 먼저 고칩니다.

예:

- 클럽 폐업/재오픈: `clubs()`
- 운영형 카드 변경: `rollingPartyTemplates()`
- 실이벤트 추가: `specialParties()`
- 오래된 잔재 삭제: `legacyPartyPrefixes()`

### 3단계. 문구를 과장하지 않기

운영형 카드라면 아래처럼 씁니다.

좋은 예:
- "공식 운영시간 기준 대표 세션 카드"
- "최근 운영 패턴을 반영한 주말 카드"
- "고정 게스트 공지가 아닌 운영형 카드"

나쁜 예:
- "이번 주 공식 메인 이벤트"
- "확정 라인업"
- "매주 반드시 진행되는 특집"

### 4단계. 동기화 실행

```bash
php artisan nightlife:sync-curated-data
```

### 5단계. 최소 검증

```bash
php -l app/Support/CuratedNightlifeData.php
php -l app/Models/Party.php
curl -I http://127.0.0.1/
curl -I http://127.0.0.1/parties
curl -I http://127.0.0.1/search?q=파티
```

### 6단계. 실제 내용 확인

아래를 눈으로 확인합니다.

- 홈에 `실이벤트` / `운영형 카드` 배지가 맞게 보이는가
- 파티 목록에서 같은 날짜/같은 클럽 중복이 줄었는가
- 검색 결과에 지난 파티가 남지 않았는가
- 상세 페이지 설명이 과장되어 있지 않은가

## 9. 운영자가 자주 하는 작업별 수정 포인트

### 케이스 A. 특정 클럽이 폐업했다

수정:
- `clubs()`에서 해당 클럽을 `is_active => false` 처리하거나 제거
- 해당 클럽의 운영형 카드/실이벤트 템플릿도 같이 제거
- 필요하면 해당 관련 prefix를 `legacyPartyPrefixes()`에 추가

체크:
- `/clubs`
- `/parties`
- `/search`
- `/nearby`

### 케이스 B. 특정 클럽은 살아 있는데 예전 반복 파티가 과장돼 있다

수정:
- `rollingPartyTemplates()`에서 문구를 보수적으로 수정
- 필요 없는 반복 카드면 템플릿 자체를 삭제
- 기존 잔재 정리를 위해 prefix를 `legacyPartyPrefixes()`에 추가

체크:
- 파티 카드 배지
- 설명 문구
- 알림 문구

### 케이스 C. 실제 특집 이벤트를 새로 추가한다

수정:
- `specialParties()`에 정확한 날짜/라인업/설명 추가

중요:
- 같은 날짜 운영형 카드가 있더라도 `partyRecords()`의 중복 억제 규칙으로 일반적으로 실이벤트가 우선됩니다.
- 그래도 slug prefix, club_slug, event_date가 정확한지 꼭 확인합니다.

### 케이스 D. 전국 다른 지역을 새로 확장한다

수정 후보:
- `Club::$areas`
- `GeoService` 지역 중심 좌표
- `CuratedNightlifeData::clubs()`
- 필요 시 대표 운영형 카드/특집 실이벤트 템플릿

체크:
- 지역 필터
- 홈 빠른 탐색
- Near Me
- 검색 자동완성

## 10. 500 에러 안 나게 작업하는 실전 원칙

### 원칙 1. 화면부터 고치지 말고 데이터 원본부터 봅니다

홈에서 500이 나면 Blade가 문제일 수도 있지만, 더 자주 발생하는 원인은:

- 잘못된 null 데이터
- 예상하지 못한 배열 구조
- 동기화 후 비정상 데이터

그래서 먼저 원본 데이터 구조를 확인해야 합니다.

### 원칙 2. 운영형 카드 문구만 바꾸는 작업도 lint를 돌립니다

문자열 하나 잘못 닫아도 홈/파티/검색 전부 같이 깨집니다.

반드시:

```bash
php -l app/Support/CuratedNightlifeData.php
```

### 원칙 3. 홈만 500이고 다른 페이지는 정상이면 서비스워커도 의심합니다

이 프로젝트는 PWA라서, 브라우저 캐시/서비스워커가 오래된 홈 HTML을 잡고 있을 수 있습니다.

확인 순서:

1. `curl -I http://127.0.0.1/` 가 200인지
2. `curl -I http://183.111.6.101/` 가 200인지
3. Laravel 로그에 실제 새 에러가 있는지
4. 브라우저 강력 새로고침 또는 서비스워커 캐시 영향인지

### 원칙 4. 홈이 정상이더라도 파티/검색/알림까지 봅니다

같은 파티 데이터가 여러 화면에서 재사용되므로 최소 이 경로는 같이 봐야 합니다.

- `/`
- `/parties`
- `/search?q=파티`
- `/tonight`
- `/notifications`

## 11. 권장 검수 주기

### 매일

- 오늘/이번 주 파티 날짜가 지난 카드가 남지 않았는지 확인
- 홈 추천 카드 라벨이 자연스러운지 확인
- 500 에러 제보가 있으면 `curl`과 로그로 먼저 재현 확인

### 매주

- 서울 외 지역도 최신 운영 흔적이 있는지 재확인
- `운영형 카드` 중 과장된 설명이 없는지 검수
- 특집 실이벤트가 끝난 뒤 남아 있는 잔재가 없는지 확인

### 매월

- 전국 클럽 중 재검증 우선 장소 재조사
- `legacyPartyPrefixes()`에 새 정리 대상이 생겼는지 점검
- `/docs` 문서와 실제 운영 방식이 달라지지 않았는지 확인

## 12. 초보 PHP 개발자를 위한 가장 안전한 명령 순서

작업 전:

```bash
php -l app/Support/CuratedNightlifeData.php
```

작업 후:

```bash
php -l app/Support/CuratedNightlifeData.php
php -l app/Models/Party.php
php artisan nightlife:sync-curated-data
curl -I http://127.0.0.1/
curl -I http://127.0.0.1/parties
curl -I http://127.0.0.1/search?q=파티
curl -I http://127.0.0.1/tonight
curl -I http://127.0.0.1/notifications
```

이 순서를 지키면:

- 문법 에러
- 동기화 실패
- 홈만 죽는 문제
- 파티/검색/추천 연쇄 장애

를 초기에 발견할 확률이 높습니다.
