# VYBE 모바일 UX 고도화 PRD (1차 실행안)

> 목적: 현재 VYBE를 "정보 탐색형 모바일 웹"에서 "빠르게 비교하고, 바로 문의하고, 다시 돌아오게 만드는 앱형 서비스"로 전환하기 위한 1차 실행 문서.
>
> 기준: 현재 코드베이스(`/var/www/nightlife`)의 사용자 웹, 관리자 웹, MD 대시보드 구조를 기반으로 작성.

---

## 1. 문서 목적

이 문서는 아래 3가지를 동시에 만족시키기 위한 실행 문서다.

1. 디자인팀이 화면 구조와 컴포넌트 원칙을 바로 이해할 수 있어야 한다.
2. 프론트엔드/백엔드 개발팀이 기능 단위로 바로 티켓을 쪼갤 수 있어야 한다.
3. 운영팀이 왜 이 작업이 필요한지와 운영 방식 변화를 이해할 수 있어야 한다.

이번 1차 범위는 다음 6개 영역에 집중한다.

1. 홈 개편
2. 리스트 화면 필터/정렬/비교 강화
3. 상세 화면 전환 구조 개편
4. 문의/예약 흐름 고도화
5. 마이페이지 액션 대시보드화
6. 관리자 운영 인박스화

---

- 반복 문의 감소

## 4. 공통 설계 원칙

### 모바일 우선 원칙

- Primary CTA는 화면당 1개만 둔다.
- 모든 주요 액션은 엄지 도달 영역 하단 40% 안에서 다시 한 번 접근 가능해야 한다.
- 긴 설명보다 상태, 가격, 응답속도, 가능 여부를 먼저 보여준다.
- 사용자의 질문은 "어디가 좋지?"보다 "지금 어디로 갈 수 있지?", "누가 빨리 답해주지?"에 가깝다.

### 전환 설계 원칙

- 사용자는 비교 없이 결정하지 않는다.
- 상세 페이지는 정보 페이지가 아니라 전환 페이지다.
- 문의는 "폼 제출"이 아니라 "예약 상담 시작"으로 느껴져야 한다.
- 운영 상태는 숨기지 말고 배지와 타임라인으로 드러낸다.

### 운영 설계 원칙

- 대기열은 기능별이 아니라 우선순위별로 묶는다.
- 반려/승인/상태변경은 이유와 로그가 남아야 한다.
- 운영자가 반복해서 쓰는 문장은 템플릿화한다.

## 5. 화면별 상세 실행안

## 5-1. 홈 개편

### 현재 문제

- 섹션이 많고 병렬적이다.
- 사용자가 첫 화면에서 할 행동이 분산된다.
- 최근 본, 응답 대기, 지금 영업 중 같은 즉시성 정보가 약하다.

### 목표

- 첫 5초 안에 탐색 시작 혹은 재진입 액션을 유도한다.
- 첫 화면에서 "오늘 갈 곳 찾기"와 "이어서 보기"를 동시에 제공한다.

### 권장 정보 구조

1. 상단 앱바
2. 메인 히어로 CTA
3. 최근 본 이어보기
4. 지금 영업 중 / 오늘 파티
5. 빠른 필터
6. 실시간 후기
7. 하단 보조 진입

### 모바일 와이어프레임

```text
[헤더]
VYBE | 위치 | 검색 | 알림

[Hero]
오늘 밤 어디로 갈까요?
지금 위치와 취향 기준으로 추천
[Primary CTA: 오늘 갈 곳 찾기]
[Secondary CTA: 지금 영업 중 보기]

[이어보기]
최근 본 클럽/파티/투어 3개 카드

[실시간 추천]
- 지금 영업 중
- 오늘 파티
- 외국인 가능

[빠른 필터 칩]
홍대 / 강남 / EDM / 힙합 / 오늘 / 5만원 이하

[커뮤니티 실시간]
실시간 후기 3건
```

### 개발 항목

- 홈 섹션 우선순위 재정렬
- `최근 본 이어보기`를 최상단으로 승격
- `오늘 추천받기` CTA를 `오늘 갈 곳 찾기`로 명확화
- 홈에서 바로 `지금 영업 중 보기`, `빠른 문의 가능한 곳` 진입 제공
- 홈 배너는 1개만 노출하고 나머지는 아래로 이동

### Acceptance Criteria

- 홈 첫 화면에 Primary CTA가 1개만 보여야 한다.
- 최근 본 데이터가 있으면 히어로 바로 아래에 노출되어야 한다.
- 홈에서 검색 진입이 1탭이어야 한다.

## 5-2. 리스트 화면 개편 (클럽/파티)

### 현재 문제

- 리스트에서 비교와 압축이 어렵다.
- 필터/정렬 구조가 약하다.
- 상태성 정보가 카드에 부족하다.

### 목표

- 사용자가 10초 안에 후보 3개로 압축할 수 있게 한다.

### 추가 UI 구조

```text
[상단 고정 바]
[필터] [정렬] [지도] [비교 0]

[필터칩]
오늘 / 영업중 / 외국인 가능 / EDM / 강남 / 5만원 이하

[리스트 카드]
썸네일
이름 / 지역 / 장르
상태 배지: 영업중, 오늘 파티, 문의 가능
가격대 / 평점 / 응답속도
[찜] [비교 추가]
```

### 필수 기능

- 바텀시트 필터
- 정렬: 추천순, 거리순, 인기순, 가격낮은순, 응답빠른순
- 지도/리스트 토글
- 비교함
- 선택 필터 고정 노출

### Acceptance Criteria

- 필터 적용 후 결과 수가 즉시 보여야 한다.
- `비교`는 최대 4개까지 추가 가능해야 한다.
- 카드에 최소 1개의 상태 배지가 보여야 한다.

## 5-3. 상세 화면 개편 (클럽/파티)

### 현재 문제

- 정보량은 충분하지만 행동 전환이 늦게 나온다.
- 스크롤 중 CTA가 사라진다.
- 신뢰를 만드는 운영 정보가 부족하다.

### 목표

- 사용자가 상세 상단 1스크린 내에서 "문의할지 말지" 판단할 수 있게 한다.

### 상단 정보 우선순위

1. 대표 이미지
2. 이름/지역/장르
3. 가격대
4. 예약 가능 여부
5. 평균 응답시간
6. 외국인 가능/영업중/오늘 파티 여부
7. 리뷰 요약

### 하단 고정 CTA

```text
[찜] [공유] [문의하기] [예약 요청]
```

### 추천 상세 구조

```text
[Hero]
이름 / 상태 배지 / 평점 / 가격

[요약 카드]
영업시간 / 위치 / 드레스코드 / 응답속도 / 예약 가능

[사진]
스와이프 가능 썸네일 + 전체보기

[리뷰 요약]
평점 / 검증 후기 / 최근 후기 3개

[FAQ]
입장 가능 / 드레스코드 / 테이블 / 외국인 / 대기

[문의 상태 카드]
현재 문의 가능 / 담당자 / 평균 응답

[하단 고정 CTA]
```

### Acceptance Criteria

- 상세 첫 스크린에서 `가격`, `상태`, `문의 가능 여부`가 모두 보인다.
- 하단 CTA는 스크롤과 무관하게 유지된다.
- FAQ가 최소 5개 항목으로 제공된다.

## 5-4. 문의/예약 흐름 개편

### 현재 문제

- 문의는 되지만 사용자에게 "진행중인 상담"처럼 느껴지지 않는다.
- 문의 후 상태 확인 동선이 약하다.
- 운영자와 사용자 모두 문의 상태 의미를 직관적으로 이해하기 어렵다.

### 목표

- 문의를 예약 여정의 시작점으로 만들고, 이후 상태를 시각화한다.

### 상태 모델

1. 접수됨
2. 담당자 배정
3. 상담중
4. 견적 제안
5. 예약 확인 대기
6. 예약 확정
7. 종료

### 사용자 화면 구성

```text
[문의 입력]
메시지
방문일 / 인원 / 예산 / 연락수단
[문의하기]

[문의 상세]
상태 타임라인
담당자 이름/역할
평균 응답시간
대화 내역
다시 알림 보내기
```

### 운영 화면 구성

```text
[운영 인박스]
긴급
응답 지연
견적 필요
확정 대기

[문의 상세 패널]
사용자 정보
희망 일정
예산
이전 문의 이력
템플릿 답변
상태 변경
내부 메모
```

### Acceptance Criteria

- 문의 생성 후 사용자는 즉시 `문의 상태` 페이지로 재진입할 수 있어야 한다.
- 문의 상태는 타임라인으로 보여야 한다.
- 운영자는 템플릿 답변을 사용할 수 있어야 한다.

## 5-5. 마이페이지 개편

### 현재 문제

- 현재는 메뉴 허브형 구조가 강하다.
- 재방문 직후 행동 유도가 약하다.

### 목표

- 사용자가 "지금 해야 할 것"을 먼저 보게 한다.

### 권장 구성

```text
[프로필]
닉네임 / 상태 / 알림 수

[진행중 액션]
- 답변 대기 문의 2건
- 오늘 예약 확인 필요 1건
- 최근 본 이어보기

[개인화]
- 찜한 곳
- 최근 본
- 관심 지역/장르

[설정]
- 알림
- 계정
- 고객센터
```

### 핵심 변화

- `진행중 문의`, `확인 필요한 알림`, `최근 본 이어보기`를 최상단 배치
- 마이페이지를 설정 화면이 아니라 액션 대시보드로 정의

### Acceptance Criteria

- 로그인 사용자는 마이 첫 화면에서 진행중 액션 카드가 보여야 한다.
- `문의`, `최근 본`, `알림` 각각 1탭 진입이 가능해야 한다.

---

## 5-6. 관리자 운영 인박스

### 현재 문제

- 운영 메뉴는 많지만 우선순위 작업 공간이 없다.
- 문의, 신고, 승인, 미디어 점검이 분산되어 있다.

### 목표

- 운영자가 로그인 후 3초 안에 오늘 처리해야 할 항목을 볼 수 있게 한다.

### 제안 구조

```text
[오늘의 운영 인박스]
1. 문의 미응답
2. 신고 대기
3. 승인 대기 미디어
4. 예약 확인 필요
5. 반려 재검토

[우측 패널]
선택된 항목 상세
- 사용자/대상 정보
- 상태
- 이전 이력
- 빠른 처리 버튼
```

### 1차 대시보드 카드

- 30분 이상 미응답 문의
- 오늘 마감 예약 요청
- 신고 누적 3건 이상 콘텐츠
- 승인 대기 미디어
- 반려 이유 미기입 항목

### Acceptance Criteria

- 운영 첫 화면에서 우선 처리 큐가 카드형으로 보인다.
- 각 카드에서 상세로 1탭 진입 가능해야 한다.
- 처리 후 다음 항목으로 연속 이동 가능해야 한다.

## 6. 공통 컴포넌트 규격

## 6-1. CTA 우선순위

- Primary: 화면당 1개, 가장 진한 색, 가장 큰 버튼
- Secondary: 보조 액션, outline 또는 약한 filled
- Tertiary: 텍스트 링크

### 예시

- 홈: `오늘 갈 곳 찾기`
- 상세: `문의하기` 또는 `예약 요청`
- 문의 상세: `답변 확인`

## 6-2. 상태 배지 체계

### 사용자 상태 배지

- 영업중
- 오늘 파티
- 예약 가능
- 문의 가능
- 응답 빠름
- 외국인 가능
- 검증 리뷰

### 운영 상태 배지

- 접수됨
- 상담중
- 확정대기
- 반려
- 재검토
- 긴급

## 6-3. 바텀시트 사용 기준

바텀시트로 처리할 항목:

- 필터
- 정렬
- FAQ
- 공유
- 신고
- 예약 옵션
- 이미지 전체보기

모달로 처리할 항목:

- 파괴적 액션 확인
- 강제 로그인 전환

---

## 7. 데이터/백엔드 변경 요구사항

## 7-1. 문의/예약

- 문의 상태 enum 확장 혹은 표준화
- 상태 변경 로그 저장
- 담당자/최초 응답시간 계산값 유지

## 7-2. 리스트/상세

## 7-3. 홈/개인화

- 최근 본 우선순위 정렬
- 사용자의 최근 행동 기반 추천 API 정리
- 저장된 필터/구독 알림 설계

## 7-4. 운영 인박스

- 문의/신고/미디어 승인 항목의 우선순위 계산 필드 필요
- 운영 처리 SLA 계산값 필요

## 10. 1차 완료 정의

다음 조건을 만족하면 1차 완료로 본다.

1. 홈에서 사용자가 1탭 내에 탐색을 시작할 수 있다.
2. 리스트에서 필터/정렬/비교가 모바일 기준으로 작동한다.
3. 상세에서 CTA가 스크롤과 무관하게 유지된다.
4. 문의 후 상태를 사용자와 운영자가 같은 구조로 본다.
5. 마이페이지에서 진행중 액션이 최상단에 노출된다.
6. 관리자 첫 화면이 메뉴가 아니라 우선처리 인박스로 바뀐다.
